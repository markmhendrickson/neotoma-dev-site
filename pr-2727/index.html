A record, not recall

The system of record for AI agents.

  • The source is available under the MIT license.
  • Run your own instance and keep its record under your control.
  • Connect an AI tool through its configured MCP server.
  • Read and write through the documented HTTP API.
  • Inspect and maintain the record from a terminal.

Give agents operational truth they can read, update, and maintain as they work.

Install

01 · Compare

Recall and a system of record answer different questions

Memory and retrieval tools help an agent keep and find context. A system of record computes current values from accepted observations and keeps a path back to the evidence for each field.

Neotoma is for developers and operators whose agents handle changing facts across tools. You choose what enters the local instance and which tools use it.

Recall compared with a system of record
QuestionRecallSystem of record (Neotoma)
What is stored?Typically a summary of what the agent saw.Each stored fact as an observation linked to its source.
What happens when a fact changes?Typically the new text sits beside the old, or replaces it.A new observation is added and the earlier one stays.
How do you see why a value is current?Typically the agent's own account.Each current field names the observation that set it.
What does a second agent read?Whatever that tool retained.The same record, when it uses the same instance and MCP entry or data profile.

02 · Follow a record

How a fact becomes current

Example

Invoice INV-2041 arrives as a PDF due October 22nd. A later supplied email changes the due date to October 29th, 2026. A connected agent reading the invoice sees the selected October 29th value and can inspect which observation supplied it. The amount still comes from the PDF.

  1. Step 01 · Source

    Keep the source

    The supplied document or message is retained as the input to this record.

    Read about sources
  2. Step 02 · Observation

    Record a fact

    Each stored fact is an observation with a path back to its source.

    Read about observations
  3. Step 03 · Entity

    Match the record

    Identity fields connect observations about the same invoice.

    Read about entities
  4. Step 04 · Reducer

    Apply the field rule

    Merge rules per field compute the current value from the observations.

    Read about field rules
  5. Step 05 · Snapshot

    Read the current value

    The snapshot shows the rule-selected field values and the observations behind them.

    Read about snapshots

One invoice, five parts

  1. 1Two sources say different things about one invoice: the PDF says due October 22nd, a later email says October 29th.
  2. 2Each source becomes an observation. A rule, last write per field here, computes the current value from them.
  3. 3The due date now reads October 29th. The changed field points to the later observation.
  4. 4The amount still comes from the first observation. Both observations stay on record.
  5. 5Agents write each source in as an observation, and read the current snapshot back out. Writes made through the MCP server also record the client name the client reports.

Local CLI commands do not add the MCP client's writer attribution.

CLI example

# Local profile. Replace each example key once; reuse it only for a retry of that same operation.

# Read the returned entity_id as INVOICE_ID.

neotoma dev store \
  --observation-source import \
  --idempotency-key unique-invoice-store-key \
  --entities '[
  {
    "entity_type": "invoice",
    "schema_version": "1.0",
    "invoice_number": "INV-2041",
    "vendor_name": "Acme",
    "invoice_date": "2026-10-01",
    "amount_due": 3200,
    "currency": "USD",
    "date_due": "2026-10-22"
  }
]'

# The supplied email changes the date. Use the entity ID returned above.

neotoma dev corrections create "$INVOICE_ID" \
  --entity-type invoice \
  --field-name date_due \
  --corrected-value 2026-10-29 \
  --idempotency-key unique-amendment-key

neotoma dev entities get "$INVOICE_ID"

neotoma dev observations list --entity-id "$INVOICE_ID"

neotoma dev request --operation getFieldProvenance \
  --body "{
  \"entity_id\": \"$INVOICE_ID\",
  \"field\": \"date_due\"
}"

The snippets are illustrative calls, never run by this page. Read the store response for the actual entity ID. Replace each example idempotency key with a unique key per operation, then reuse that key and payload only to retry that operation. A correction adds an observation; it does not edit the earlier one. The snippets store fields and inspect their history, but do not upload the fictional PDF or email. Observation history is distinct from date-derived timeline events.

The connected MCP client reports its identity; verification depends on signed requests.

03 · Connect

Start in your favorite AI tool

Neotoma runs as a local service. Connected agents use the Model Context Protocol (MCP), REST API or CLI to read and write records in a configured instance.

Point each tool at the same instance and data profile to work with the same records; separate entries can use separate databases. The bundled app lets you examine them.

Manual install

Run these commands yourself on the host machine.

npm install -g neotoma
neotoma init
neotoma setup --tool claude-code

Read the Claude Code guide for the supported connection path. The install guide covers the local service.
