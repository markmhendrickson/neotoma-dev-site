01 · Compare

## Recall and a system of record answer different questions

Memory and retrieval tools help an agent keep and find context. A system of record computes current values from accepted observations and keeps a path back to the evidence for each field.

Neotoma is for developers and operators whose agents handle changing facts across tools. You choose what enters the local instance and which tools use it.

Scattered paper fragments

Without a system of record

### An agent recalls only what its context retained.

Relevant facts remain scattered across separate pieces of context, with no explicit current value selected here.

Paper fragments filed into one record

With a system of record

### Agents retrieve current facts, historical changes, and their sources.

One record presents the selected field values while keeping their supporting observations connected.

1.  ### What is stored?
    
    Recall
    
    Typically a summary of what the agent saw.
    
    System of record
    
    Each stored fact as an observation linked to its source.
    
2.  ### What happens when a fact changes?
    
    Recall
    
    Typically the new text sits beside the old, or replaces it.
    
    System of record
    
    A field rule selects the current value from the observations; earlier observations stay in history.
    
3.  ### How do you see why a value is current?
    
    Recall
    
    Typically the agent's own explanation.
    
    System of record
    
    Each current field names the observation that set it.
    
4.  ### What does a second agent read?
    
    Recall
    
    The context saved in that agent’s tool, which may differ from another agent’s.
    
    System of record
    
    The same record, when it uses the same instance and MCP entry or data profile.

02 · Follow a record

## How a fact becomes current

Example

Invoice INV-2041 arrives as a PDF due October 22nd. A later supplied email changes the due date to October 29th, 2026. A connected agent reading the invoice sees the selected October 29th value and can inspect which observation supplied it. The amount still comes from the PDF.

1.  Step 01 · Source
    
    ### Store the raw source material
    
    Supply the invoice PDF or email as source material so its contents remain available for inspection.
    
    [Read about sources](/provenance/)
    
    An original document and email remain whole in one shallow archive pocket, before any interpretation
    
2.  Step 02 · Observation
    
    ### Extract and record facts
    
    An agent extracts the invoice fields from the PDF and the revised due date from the later email. It records each as an observation linked to its supplied source.
    
    [Read about observations](/observations/)
    
    An original invoice and a later email each produce a retained observation, with the later email revealing its revised date
    
3.  Step 03 · Entity
    
    ### Identify entities deterministically
    
    The invoice number, vendor and invoice date identify this invoice; later observations can refer to it.
    
    [Read about entities](/record-model/)
    
    Two observations carry the same type and identifying marks into one stable entity dossier
    
4.  Step 04 · Current values
    
    ### Compute current values from observations
    
    Neotoma applies the schema’s field rule automatically. Here, the later due date becomes current while the PDF still supplies the amount.
    
    [Read about field rules](/schemas/)
    
    One fact slip selected from each visible stack and linked to a row on a record card
    
5.  Step 05 · Snapshot
    
    ### Read the current value
    
    The snapshot shows the rule-selected field values and the observations behind them.
    
    [Read about snapshots](/current-snapshot/)
    
    A current record presents two rule-selected fields while earlier observations remain behind it
    

One invoice, five parts

An invoice and later email feed separate retained observations; the current record keeps the amount from the invoice and due date from the email

1.  1Two sources say different things about one invoice: the PDF says due October 22nd, a later email says October 29th.
2.  2Each source becomes an observation. A rule, last write per field here, computes the current value from them.
3.  3The due date now reads October 29th. The changed field points to the later observation.
4.  4The amount still comes from the first observation. Both observations stay on record.
5.  5Agents write each source in as an observation, and read the current snapshot back out. Writes made through the MCP server also record the client name the client reports.

```
# Use the intended API and its configured CLI credential.
# Work in a private directory with your supplied source files.
# Protect generated extraction JSON from other local users.
umask 077
# The API must be able to read these source-file paths.
# Replace each example key once for a new operation.
# Retry an unchanged operation with the same payload and keys.
# Changed facts, changed bytes or a new extraction require a new write key.

neotoma --api-only --base-url "$NEOTOMA_URL" --json store \
  --file invoice.extracted.json \
  --file-path invoice.pdf \
  --interpretation-source-ref unstructured \
  --interpretation-config '{"extractor_type":"agent","schema_version":"1.0"}' \
  --observation-source llm_summary \
  --idempotency-key demo-inv2041-pdf-write-v1 \
  --file-idempotency-key demo-inv2041-pdf-bytes-v1 \
  --strict

# Read structured.entities[0].entity_id from the response.
# Set INVOICE_ID to that returned ID, not the invoice number.
INVOICE_ID='REPLACE_WITH_RETURNED_ENTITY_ID'

# Only date_due is attributed to the later email.
python3 - "$INVOICE_ID" > email.extracted.json <<'PY'
import json, sys
print(json.dumps([{
    "entity_type": "invoice",
    "schema_version": "1.0",
    "target_id": sys.argv[1],
    "date_due": "2026-10-29"
}]))
PY

neotoma --api-only --base-url "$NEOTOMA_URL" --json store \
  --file email.extracted.json \
  --file-path due-date-email.txt \
```

make-source-store.py · upload actual source bytes

```
import base64
import hashlib
import json
import pathlib
import sys

source = pathlib.Path(sys.argv[1])
entities = json.loads(pathlib.Path(sys.argv[2]).read_text())
write_key = sys.argv[3]
mime_type = sys.argv[4]
raw = source.read_bytes()

print(json.dumps({
    "entities": entities,
    "file_content": base64.b64encode(raw).decode("ascii"),
    "mime_type": mime_type,
    "original_filename": source.name,
    "idempotency_key": write_key,
    "file_idempotency_key": hashlib.sha256(raw).hexdigest(),
    "interpretation": {
        "source_ref": "unstructured",
        "interpretation_config": {
            "extractor_type": "agent",
            "schema_version": "1.0"
        }
    },
    "observation_source": "llm_summary",
    "strict": True
}))
```

## Start in your favorite AI tool

One chosen AI tool card reaches a configured local archive containing multiple records

Neotoma can run locally or behind an authenticated endpoint. Connected agents use MCP, REST API or CLI to read and write records in a configured instance.

Point each tool at the same instance and data profile to work with the same records; separate entries can use separate databases. The bundled app lets you examine them.

05 · Advanced

## Grow your use as advanced capabilities arrive

Three distinct connected tool slips lead to one shared Neotoma filing box

Supported

### A shared system of record

Teams and collaborators can work with the same records through configured access to one instance and data profile.

[Read the guide](https://github.com/markmhendrickson/neotoma/blob/main/docs/integrations/matrix.md)

An admitted signed request and a separate active scoped grant both precede a bounded record action

Supported

### Verified identity and scoped access

An admitted signed request can establish agent identity; active scoped grants determine permitted actions. Other paths may have self-reported or absent writer identity.

[Read the guide](https://github.com/markmhendrickson/neotoma/blob/main/docs/use_cases/agent_auth.md)

Two distinct instances exchange only selected record slips in both directions

Supported

### Selected record exchange

Configured peers exchange selected records between separate instances, without claiming complete history, files or deletions.

[Read the guide](https://github.com/markmhendrickson/neotoma/blob/main/docs/subsystems/peer_sync.md)

Planned domain ownership: an authority key reaches one bounded archive while a second domain stays separate

Planned

### Bounded domain ownership

Planned domain ownership would make clear who may correct each bounded part of the record.

[Read the guide](https://github.com/markmhendrickson/neotoma/blob/main/docs/foundation/core_identity.md)
