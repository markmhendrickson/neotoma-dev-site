Neotoma · the system of record for AI agents

A record, not recall.

Neotoma is the system of record for AI agents. Without one, an agent works from whatever it happens to recall: part of the last session, a note its tool saved, or nothing. With one, it reads what was stored, from which source, and what is current now, so the agents you connect can defer to one answer.

Open source (MIT) · local-first · MCP server, REST API and CLI

Sheet 02 · Schedule

Recall and record answer different questions

Memory and retrieval tools help an agent keep and find context. A record takes on a different job. It computes the current value from accepted observations and keeps a path back to the evidence for each field. The two overlap, and a product can cover more than one.

Recall compared with a record
MarkQuestionRecallRecord (Neotoma)
R1What is stored?Typically a summary of what the agent saw.Each stored fact as an observation linked to its source.
R2What happens when a fact changes?Typically the new text sits beside the old, or replaces it.A new observation is added and the earlier one stays.
R3How do you see why a value is current?Typically the agent's own account.Each current field names the observation that set it.
R4What does a second agent read?Whatever that tool retained.The same record, when it is connected to the same MCP entry.

Sheet 03 · Section A-A

How a fact becomes current

  1. 1

    Source

    Raw input is stored once, content-addressed.

  2. 2

    Observation

    Each extracted fact is stored as an observation linked to its source.

  3. 3

    Entity

    The type's identity fields map the observation to an entity.

  4. 4

    Reducer

    Merge rules per field compute the current value from the observations.

  5. 5

    Snapshot

    The current entity, with a map from each field to the observation behind it.

A correction is one more observation. It does not edit the earlier one, so the original value is still listed and every current field names the observation that set it. The run below was run on the published npm package (0.25.0) and on main, with the invoice from sheet 01 plus one correction. The commands start with neotoma dev because a plain npm install points the CLI at the production profile, which needs a token. Output is reformatted from the CLI's JSON to fit the page. Store observation ids differ between installs; yours will not match these.

$ neotoma dev store --observation-source import --entities '[{"entity_type":"invoice",
    "invoice_number":"INV-2041","vendor_name":"Acme","invoice_date":"2026-10-01",
    "amount_due":3200,"currency":"USD","date_due":"2026-10-22"}]'
$ neotoma dev store --observation-source llm_summary --entities '[{"entity_type":"invoice",
    "invoice_number":"INV-2041","vendor_name":"Acme","invoice_date":"2026-10-01",
    "date_due":"2026-10-29"}]'
$ neotoma dev corrections create ent_7cbcf2519f652626f3fe292a --entity-type invoice \
    --field-name amount_due --corrected-value 3250

$ neotoma dev entities get ent_7cbcf2519f652626f3fe292a
  observation_count   3
  amount_due          3250        set by b7e0392c (correction)
  date_due            2026-10-29  set by 5e29854e (llm_summary)
  currency            USD         set by f640b9f1 (import)

$ neotoma dev observations list --entity-id ent_7cbcf2519f652626f3fe292a
  b7e0392c  correction   amount_due=3250
  5e29854e  llm_summary  date_due=2026-10-29
  f640b9f1  import       amount_due=3200, date_due=2026-10-22, currency=USD

Sheet 04 · Schedule of connections

One local service, read by the tools you connect

Neotoma runs as a local service. Agents reach it through an MCP server, a REST API or the CLI, and you inspect it in a bundled web app. Agents connected to the same MCP entry read and write the same record.

Hosts with a one-command setup
MarkHostSetup command
H1Claude Codeneotoma setup --tool claude-code --yes
H2Cursorneotoma setup --tool cursor --yes
H3Codex CLIneotoma setup --tool codex --yes

Sheet 05 · Install

Install in a few minutes

npm install -g neotoma
neotoma init
neotoma setup --tool claude-code --yes

Using another host? Swap claude-code for the tool name in the setup column of the sheet 04 table. To print the MCP entry for another client, run neotoma mcp config in a terminal; it asks which one.

Sheet 06 · General notes

What this drawing does not show

What to expect

  1. A record is a working commitment.

    Agents have to write to it and read from it. Neotoma needs a local service and deliberate writes, and it does nothing for facts that never reach it.

  2. Provenance is a trail, not a verdict.

    It shows which observation set a field and where that came from. It does not show that an agent read the source correctly. Repeatable results are not proof of what is true in the world.

  3. Not a chat log or a vector store.

    Neotoma stores typed entities and their observations. It can sit beside tools that retain or retrieve context.

Not built yet

  1. Reading the whole record as it stood at a past date.

    One entity can be read as of a past time today. The whole record cannot.

  2. Moving a record between instances with its history.

    The export command writes the current value of each entity as JSONL. Observation history stays in the instance it was recorded in.

  3. Corrections that always hold.

    A later ordinary write can replace a correction.

  4. Verified authorship for every write.

    Attribution is verified only for signed requests. Otherwise the name is the writer's own report, and some write paths, such as the CLI, record no writer.

A local install serves one operator; there are no organizations, workspaces, or rules for who may correct what. Known defects and edge cases are listed in known limitations.
