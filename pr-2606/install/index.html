Agent-assisted install

If you want to skip the initial evaluation page and proceed directly from install, paste this prompt into Claude, Codex, Cursor, or a similar agent. The prompt stays intentionally short; this page documents the full install-first sequence it should follow.

Agent prompt
Paste this into an assistant to run the install-first Neotoma flow.
Read https://neotoma.io/install and carry me through the install-first Neotoma flow.

Use `neotoma` commands for status and setup. If Neotoma is already installed, start with `neotoma status --json`; otherwise install it and run `neotoma setup --tool <my_tool> --yes`.

Avoid ad-hoc shell introspection or arbitrary repo scripts. Then store my first records and configure my current tool for ongoing use.

This page expands the prompt. The copied prompt omits detail for readability; the full install-first flow here includes:

  1. Confirming the user wants the install-first path and identifying the current tool.
  2. Installing only if needed, then verifying configuration and connectivity with neotoma status --json.
  3. Choosing the first data to store and the onboarding mode.
  4. Running activation, then configuring the current tool for ongoing use.

Expanded install-first sequence

Use this path only when the user already wants to proceed with Neotoma and does not need the broader fit-assessment flow on /evaluate.

  1. Confirm the install-first path - verify that the user wants to proceed now, identify their current tool, and note any major tool constraints that affect setup quality.
  2. Install only if needed - check whether Neotoma is already installed. If not, branch by tool: for OpenClaw, prefer openclaw plugins install clawhub:neotoma; for other local tools, run npm install -g neotoma. Then collapse the rest of setup into two calls: neotoma status --json to check configuration and connectivity and neotoma setup --tool <tool> --yes to apply init + MCP + CLI instructions + permission files idempotently. If Neotoma is already installed, just run neotoma status --json to verify.
  3. Do not improvise shell introspection. Do not run python3 -c, grep -r, ls, cat, jq, find, which, or node -e to introspect Neotoma, and do not run arbitrary npm run scripts from the user's repositories. If a permission prompt appears for anything other than neotoma * or npm install -g neotoma, stop and ask the user to widen the allowlist (see the Permissions pre-flight block below) rather than substituting another command.
  4. Set the first data target - determine what data should be stored first and, if needed, ask the user which onboarding mode they want: quick win, guided, or power user.
  5. Run activation - run the activation sequence: discover candidates, preview them, ingest confirmed sources, then query and correct.
  6. Configure the current tool - after first value is visible, set up the strongest ongoing Neotoma workflow for the tool in use. For OpenClaw, keep the native plugin path as the default and use manual MCP wiring only as fallback. If that tool is too constrained, say so explicitly and recommend a better-supported primary environment.

If your agent requires command allowlists, use the pre-flight snippets before running the prompt.

Permissions pre-flight (copy once, before running the agent prompt below)

Paste this snippet into the right file for your agent harness so the rest of onboarding only needs two approvals: neotoma * and one npm install -g neotoma. Without this, directory-scoped harnesses will prompt for every individual command.

Using OpenClaw? Skip this — the native plugin handles consent. Just run openclaw plugins install clawhub:neotoma and approve the plugin permission prompt once.

JSON merge into Claude Code's permissions file.

Target: .claude/settings.local.json (project) — or ~/.claude/settings.json (user)

// Paste into .claude/settings.local.json (project) or ~/.claude/settings.json (user).
// Merge with any existing "permissions.allow" list.
{
  "permissions": {
    "allow": [
      "Bash(neotoma:*)",
      "Bash(npm install -g neotoma:*)"
    ]
  }
}

What changes on your system

npm install -g neotoma adds a CLI binary. neotoma init creates a config directory, two local SQLite databases (development and production profiles) and an env file, and by default adds a Neotoma entry to Cursor's MCP config (~/.cursor/mcp.json). Run neotoma init --interactive to choose each step.

neotoma setup --tool <tool> --yes writes more: two MCP entries (neotoma-dev and neotoma, with separate databases), CLI instruction files for Claude Code, Cursor and Codex in the project, and two allow rules, Bash(neotoma:*) and Bash(npm install -g neotoma:*). The first lets Claude Code run any neotoma command without asking, including destructive ones such as neotoma reset; --skip-permissions writes no rules. It also installs 12 user-level skills under ~/.claude when that directory exists and, when claude is on your PATH, the Claude Code plugin (5 hooks) through two claude plugin commands; without claude on your PATH it exits with code 1 after writing the rest. Nothing runs in the background unless you start it.

No telemetry. The interactive CLI checks the npm registry for a newer version about once a day (off with --no-update-check or NO_UPDATE_NOTIFIER=1). The stdio MCP server checks when a session starts and about every 6 hours after (off with NO_UPDATE_NOTIFIER=1; --no-update-check applies to the CLI only). Agents can also call the npm_check_update tool, which makes the same request and is not turned off by NO_UPDATE_NOTIFIER. The request carries only the package name, and the registry sees ordinary connection metadata such as the address.

neotoma reset backs up local state to a timestamped directory before removing it. It runs npm uninstall -g neotoma only when run from inside a Neotoma repository; elsewhere it skips the global uninstall. If your .env sets NEOTOMA_DATA_DIR, that directory is protected and not removed.
