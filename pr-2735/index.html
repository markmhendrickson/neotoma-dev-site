01 · Compare

Recall and record answer different questions

Memory and retrieval tools help an agent keep and find context. A record takes on a different job. It computes the current value from accepted observations and keeps a path back to the evidence for each field. The two overlap, and a product can cover more than one.

Neotoma is for developers and operators whose agents handle changing facts across tools. You choose what enters the local record and which tools use it. If your existing tools already maintain a source-backed record, they may be sufficient.

02 · Follow a record

How a fact becomes current

Example

Invoice INV-2041 arrives as a PDF due 22 October. A later email moves the due date to 29 October, and the date is entered as a correction. A connected agent reading the invoice sees the selected 29 October value and can inspect which observation supplied it. The amount still comes from the PDF.

    Keep the source

    The supplied document or message is retained as the input to this record.

    Record a fact

    Each stored fact is an observation with a path back to its source.

    Read the observation reference
  3. Step 03 · Entity

    Match the record

    Identity fields connect observations about the same invoice.

    Read the entity reference
  4. Step 04 · Reducer

    Apply the field rule

    Merge rules per field compute the current value from the observations.

    Read the reducer reference
  5. Step 05 · Snapshot

    Read the current value

    The snapshot shows the rule-selected field values and the observations behind them.

    Read the snapshot reference

One invoice, five parts

  1. 1Two sources say different things about one invoice: the PDF says due 22 October, a later email says 29 October.
  2. 2Each source becomes an observation. A rule, last write per field here, computes the current value from them.
  3. 3The due date now reads 29 October. The changed field points to the later observation.
  4. 4The amount still comes from the first observation. Both observations stay on record.
  5. 5Agents write each source in as an observation, and read the current snapshot back out. Writes made through the MCP server also record the client name the client reports.

The current record selects a value for each field and keeps its observation trail.

Three interfaces

Illustrative calls, never run by this page. Read the store response for the actual entity ID. The snippets record fields and their observation history; they do not upload the fictional PDF or email shown above. Over MCP and REST, each store and each correction needs its own idempotency key (the CLI generates one). A correction does not edit the earlier observation, and it stores no source document.

Local CLI commands do not add the MCP client's writer attribution.

CLI example

# Local profile. Read the returned entity_id as INVOICE_ID.

neotoma dev store \
  --observation-source import \
  --entities '[
  {
    "entity_type": "invoice",
    "schema_version": "1.0",
    "invoice_number": "INV-2041",
    "vendor_name": "Acme",
    "invoice_date": "2026-10-01",
    "amount_due": 3200,
    "currency": "USD",
    "date_due": "2026-10-22"
  }
]'

# The supplied email changes the date. Use the entity ID returned above.

neotoma dev corrections create "$INVOICE_ID" \
  --entity-type invoice \
  --field-name date_due \
  --corrected-value 2026-10-29

neotoma dev entities get "$INVOICE_ID"

neotoma dev observations list --entity-id "$INVOICE_ID"

neotoma dev request --operation getFieldProvenance \
  --body "{
  \"entity_id\": \"$INVOICE_ID\",
  \"field\": \"date_due\"
}"

The connected MCP client reports its identity; verification depends on signed requests.

  "entity_id": "$INVOICE_ID",

REST requires configured authentication; unsigned writer names are self-reported.

All three paths store, amend, read the snapshot and inspect observations and field provenance. In a default local install the stdio MCP server and the CLI or REST API write as different local users, so they keep separate records unless they share an instance and user. Observation history is distinct from date-derived timeline events.

03 · Connect

Start in your favorite AI tool

Neotoma runs as a local service. Connected agents use the Model Context Protocol (MCP), REST API or CLI to read and write a configured instance. Point each tool at the same instance and data profile or MCP entry to share a record; separate entries can use separate databases. The bundled Inspector lets you examine the record.

Manual install

Run these commands yourself on the host machine.

npm install -g neotoma
neotoma init
neotoma setup --tool claude-code

These human-run commands omit --yes. Setup still makes some changes automatically, including initialization and certain configuration writes; omission is not a general approval gate. Review the full install guide and run neotoma status --json to check the result. Automated setup may use --yes after its operator has authorized the changes.

Other documented integrations: ChatGPT, Windsurf, Continue, VS Code, IronClaw and Letta use MCP or an HTTP connector, configured by hand, and OpenCode uses MCP. See integrations for each guide.

04 · Direction

Where this is going

A record people and agents maintain together. The source, observation and snapshot foundation is here today. These ambitions extend it toward clearer authority over state.

Planned direction · 01

Give each domain a clear owner

Define who may correct which part of the record, with authority scoped to the domain.

Planned direction · 02

Keep disagreement on the record

Represent competing claims, unresolved disputes and official positions explicitly.

Planned direction · 03

Make authority easier to inspect

Show why a value holds, whose authority it follows and what a change would affect.

Planned governance, with no promised timeline. Authority to act stays in the operational tools above the record. See vision status.

Current scope and limits

Current boundaries: one local operator; later ordinary writes can replace corrections; export contains current values without observation history; authorship is verified only for signed requests, and some paths record no writer. One entity can be read as of a past time; the whole record cannot. Read the known limitations.
